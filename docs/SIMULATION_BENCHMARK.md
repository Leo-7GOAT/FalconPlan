# Simulation benchmark — stage evidence

Environment: Windows 10 build 19045; Ubuntu 22.04 / WSL2 kernel 6.18.40.1, x86-64; AMD Ryzen 5 9600X (6 cores / 12 logical CPUs), 63.65 GiB host RAM, RTX 5060 Ti. Python 3.11 Windows / 3.10 WSL. CARLA client/server 0.9.15, Town10HD_Opt, dt .05 s, .01 s physics substeps. Ground truth supplies vehicle/actor localization. Seeds 7/19 and sample counts are recorded; deterministic baseline routes repeat identically when no parameter is randomized. This is a small scenario study, not ODD statistical certification.

## Raw evidence

- `artifacts/carla/regression.json`: initial PID 14 runs, 240 samples / 12 s each. Early acceleration fields were clipped and are excluded from physical acceleration claims.
- `artifacts/carla_full_stack_v4/regression.json`: actual behavior → lattice → ST-DP → QP → parameterization → MPC → Stanley → safety → HAL, 400 samples / 20 s each. Following CTE .0001273 m, speed RMSE .8387 m/s, min gap 5.3801 m, displacement 53.9749 m; static avoidance CTE .08022 m, speed RMSE .54697 m/s, displacement 61.6098 m. Zero collisions. Raw acceleration 13.37/13.41 m/s² means physical constraints **PARTIAL**, despite an early motion-pass summary label.
- `artifacts/carla_full_stack*`: retained rejected planning, no-motion and native Ackermann collision experiments. Zero collisions without actual movement prompted an explicit displacement gate.
- `artifacts/carla_calibration/`: real automatic-transmission sweep, 5 throttle levels × 160 samples, peaks 12–15 m/s².
- `artifacts/carla_calibration_manual/`: same sweep, manual first gear; throttle .1/.15/.2/.25/.3 native acceleration peaks 2.09/2.12/2.34/2.50/3.03 m/s². These are CARLA Tesla measurements, not R550 calibration.
- `artifacts/dynamics/benchmark.json`: analytical models only, 5 × 1,000 steps. Delay .2 s, friction .7, v=10: CTE .58757 m with gain 1.5 versus .33005 with gain .6. Friction .4 at 20 m/s: **FAIL**, CTE 38.76 m.
- `artifacts/cpp/parity.json`: 1,000 seed-42 cases, max absolute Python/C++ difference 1.42e-14.
- `artifacts/carla_regression_final/regression.json`: seven scenarios × seeds 7/19, 240 steps each, C++ Stanley / Python PID. All 14 motion and ideal-sensor diagnostic gates passed with zero collisions; **all 14 overall PARTIAL**. Normal-scene maximum absolute raw acceleration 3.10–3.70 m/s² exceeds the +3 target in some cases; emergency timeout stop deceleration 22.82–26.88 m/s² and jerk 316–508 m/s³. Normal-scene jerk 87–106 m/s³ exceeds nominal 6. This suite uses fixture geometry; it does not replace online planner tests.
- `artifacts/carla_cpp_stack/regression.json`: first four real C++ full-stack runs. Static seed 7 **FAIL** from negative initial-speed rejection during slight standstill rollback; all collision counts zero. The failure is retained.
- `artifacts/carla_cpp_recovery_verified/regression.json`: following/static seed 7 rerun after explicit forward-only standstill projection and MPC post-solve checks. Actual motion 54.175/62.096 m, CTE RMSE .000088/.096685 m; motion, strict +3/−6 acceleration and ideal estimation pass, but measured jerk 87.021/78.646 m/s³ means overall **PARTIAL**. Genuine reverse below −.1 m/s remains rejected. Planner P95 327.270/87.117 ms, controller P95 48.073/44.082 ms. C++ Stanley executes through the shared library in the actual live loop.
- `ros2/evidence/carla/acceptance.json`: real ROS 2/CARLA topic/service/TF/rosbag acceptance. 802 samples; latency P50/P95/P99 .641/.950/1.350 ms, timer interval 9.993/10.630/10.778 ms, jitter σ .348 ms.

## Statistics and limits

Updated `artifacts/carla_sensor_v2/regression.json` has four 20 s runs after manual first-gear control, acceleration feedback and sensor sanity checks. Motion and acceleration envelopes pass; maximum actual acceleration 2.885–2.921 m/s². Position estimator RMSE .0726/.0755/.1038/.0850 m, 292–307 accepted GNSS updates and zero GNSS outliers. The initial sensor version diverged in 3/4 runs because an uninitialized newly spawned IMU derivative poisoned prediction. Impossible IMU packets are now rejected and counted; this run rejected two in one case. These are ideal-sensor diagnostics with truth-controlled localization, not sensor-localized control. Measured jerk remains 78–87 m/s³ versus nominal 6, so top-level status is **PARTIAL** and the runner exits nonzero.

`artifacts/cpp/binding.json` reports 10,000 in-process C++ Stanley calls through ctypes, seed 42 and exact numerical parity. Python P50 .650 µs, C++ plus FFI P50 1.083 µs in this checkpoint; the tiny scalar kernel is not a demonstrated speedup. Null pointers, NaN, reverse speed and invalid integration time are checked at the C ABI. Six GoogleTests pass in both Release and ASan/UBSan builds, including the shared-library boundary. The C++ controller runs inside CARLA with `--cpp-lib`, while the planning/MPC executive remains Python.

RMSE = sqrt(mean(error²)), all samples including startup unless stated otherwise. NumPy percentiles summarize host wall-clock runtimes. Command limits and physical measurements are separate; updated logs use unclipped speed finite differences for acceleration/jerk. A motion run needs displacement, no collision/solver rejection, CTE acceptance, safe following gap or completed obstacle passing. Physical acceleration failures remain PARTIAL/FAIL and return a nonzero exit code.

V4 full-chain following planner P95 381 ms, static planner P95 109 ms; controller P95 55/61 ms includes MPC solves. These are not 20 Hz deadline passes. Planning uses a 2 Hz cadence. The C++ library is tested but the executive is not a certified real-time C++ stack. Profiling uses kernel-accounted CPU and sampled process-tree RSS; shared pages can be counted twice and short peaks missed. No Pi HIL numbers are claimed.

`artifacts/final_stage_regression.json` profiles the 526-test WSL suite: process wall 7.192 s, user/system child CPU 2.897/1.097 s, maximum sampled process-tree RSS 108,154,880 bytes (636 samples). Pytest itself reports 6.82 s. These host measurements include test overhead and are not a live control-loop or Raspberry Pi performance result.
